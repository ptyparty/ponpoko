Default to using Bun instead of Node.js.

- Use `bun <file>` instead of `node <file>` or `ts-node <file>`
- Use `bun test` instead of `jest` or `vitest`
- Use `bun check` instead of `tsc --noEmit`
- Use `bun install` instead of `npm install` or `yarn install` or `pnpm install`

## Layout

- `src/events.ts`: the facts ponpoko records. They never change once written, and hold references, not text.
- `src/store.ts`: the SQLite file of facts, in `$XDG_STATE_HOME/ponpoko/`.
- `src/model.ts`: strands (a tree of lines of work, some planned: nobody's move until a move lands on them or you start them), players, the moves players make on strands, and links, rebuilt by replaying the facts. Whose move a strand is comes from its open moves, rolled up to the strands above.
- `src/core.ts`: the service, a knowledge base of strands, players and moves, testable without sockets; `src/server.ts` puts it on `$XDG_RUNTIME_DIR/ponpoko/ponpoko.sock`, and `src/client.ts` talks to it. The service knows nothing of komux: a place is opaque to it beyond its adapter, handle and directory, and it has no idea of going anywhere.
- `src/komux/`: everything komux. `bridge.ts` is `ponpoko komux`, which the komux plugin runs once per session: it reads that session's event stream, turns agent turns and failed jobs into moves through `translate.ts`, tells the service which players and tabs are present, sets tab badges, and titles `sc-*` strands from Shortcut through `src/shortcut.ts`, which reads `SHORTCUT_TOKEN` from komux's environment. `go.ts` focuses a pane or opens a tab, preferring the strand's own place, then the komux project named like the deepest strand on its path (`projects.ts` reads komux's project roots), then an ancestor's place, and picks a strand up by resuming or starting a Claude, only ever in the komux session it runs in. `for.ts` is `ponpoko for STRAND -- COMMAND`, which tells the service the komux job it runs in works for that strand (a generic `player-for` link the translator reads). `self.ts` gives the MCP the agent's own place handle.
- `src/github.ts`: asks GitHub through `gh` for pull requests waiting for a review, unanswered mentions, and your own open pull requests, and decides each one's state. `src/inbox.ts` turns that into strands under the `reviews` and `mentions` inbox strands, and into moves on the strands your own pull requests are linked to (by an agent's `status`, or by a story's name in the branch); both are recorded with source `github` and react only when a state changes. Each own pull request keeps its state in a bookkeeping `github-pr-state` link on its strand, which `ownPrs` reads back for the screens, and a review on a public repository carries a `github-repo-state` link so the Reviews area can put internal ones first. The bridge polls every two minutes, or about 15 seconds after something happens on a review or on a strand with a pull request, or after a new pull request is linked. Going to a review opens komux's `pr-review` layout by repo.
- `src/unreviewed.ts`: the count of team pull requests nobody has reviewed, which the bridge saves after each poll and `ponpoko tray --unreviewed` shows, coloured by thresholds from the config.
- `src/remax.ts`: opens the remax tour a strand links to, through `remax do` aimed at the komux tab go landed in.
- `src/render.ts`: the rows `ponpoko list` prints, and what both screens say about a strand: its glyph, the headline (the nearest titled strand, then the strand or its pull request), and a short line on who has it.
- `src/tab.ts`: the command tab, the map. `TabController` holds its keys and state, so it tests without a terminal; `src/screen.ts` is the small raw-terminal layer it draws through.
- `src/map.ts`: the command tab's areas: Work (epics with their stories, then other work, with chains of queued stories and a story's own strands folded), Reviews (your PRs, the pool nobody has reviewed, and what's already reviewed) and Mentions, and the search across them.
- `src/shortcut.ts` and `src/epics.ts`: titles from Shortcut, an epic's stories with their "blocks" links (read-only, with `SHORTCUT_TOKEN`), and the facts that bring them in as strands under the epic, planned until started, with waits between them; a bookkeeping `shortcut-import-state` link marks an epic as imported, and each story carries a `shortcut` link to its page. The service computes and records an import in one step (`import-epic`), so imports from several bridges or a refresh can't duplicate stories; `refreshEpic` in `src/actions.ts` runs it on demand. It adds only stories in a ready, started or done workflow state (`stageOf` in `src/shortcut.ts`, with ready state names from `shortcut.readyStates` in the config), skips waits you removed (a strand's `released`) and stories you forgot, and forgets stories it made (`madeBy`) that are untouched and no longer ready. The `@2` on the import link makes epics imported under the older rule run once more.
- `src/epic.ts`: `ponpoko epic ID`, the dependency view of an epic's stories (`EpicController`, also opened from the command tab), laid out by dependency depth with forks, joins and long arrows routed through the gaps between rows, and its mermaid form.
- `src/deal.ts`: the deck `ponpoko deal` shows in a komux popup, the to-do list: your moves grouped by what you'll do, everything else by who has it, with strands waiting on strands and snoozed ones folded. `Dealer` holds its keys and sections.
- `src/when.ts`: reads a typed snooze time such as `14:30`, `mon 9`, `2h` or `nov 12`.
- `src/setup.ts`: `ponpoko setup`: the `ponpoko.service` user unit, the komux plugin dropped in `~/.config/komux/plugins/`, the skill link (`src/links.ts` is copied from quoll) and the MCP. It never edits komux's config.
- `src/mcp.ts`: `ponpoko mcp`, the MCP server agents report through (`status`, `wait`, `done`, `split`) and ask (`moves`, `strand`, `changes`). It learns the agent's pane from `KOMUX_SESSION` and `KOMUX_PANE_ID`.
- `skills/ponpoko/`: the agent skill.

## Testing

- Test the service through `Ponpoko` in `src/core.ts` with a `Store(":memory:")`. `src/test-harness.ts` wires a bridge to an in-memory service, so tests can feed it komux lines. It sets `PONPOKO_PROJECT_ROOTS` to nothing, so tests never read your komux config; set it in a test's env to give it projects.
